    How This Book Works

    Three ideas that make everything after this page easier to follow.

    Read → Run → Break → Explain

    You are not expected to memorize syntax. You are expected to type every example yourself, run it, and then break it on purpose to see what the error looks like. That last step matters more than people think — a data engineer's real job is reading error messages calmly and figuring out what they mean.

    1. Code Along

    Don't just read the code blocks — retype them in your own editor. Typing builds muscle memory that reading never will.

    2. Break It on Purpose

    Misspell a column name. Remove a comma. Read the error. This is how you stop being afraid of red text.

    3. Explain It Back

    After each lesson, say out loud (or write one sentence) what the code does. If you can't, re-read the lesson.

    Meet BrightCart: Your Case Study

    Every code example, every SQL query, and every mini-project in this book — across all three phases — uses the same small dataset: a fictional online store called BrightCart. Real data engineering work is never a random toy example per lesson; you follow one system end to end. This book does the same thing on purpose.

    BrightCart sells electronics, home goods, apparel, and books. Its data has exactly the shape you'll meet in a real job: customers who sign up, products with prices, orders that get placed, and order line items — plus some orders that are still pending, cancelled, or refunded, because real businesses aren't tidy.

    The BrightCart schema — one customer places many orders, one order can contain many order_items, and every order_item points at one product.

    TableGrain (one row =)Used to teach

    productsone item BrightCart sellsjoins, categories, pricing logic

    Why a fake store and not a "real" public dataset?

    Public datasets are messy in ways that distract from the lesson at hand. BrightCart is small enough to hold in your head (16 customers, 14 products, 45 orders) but shaped exactly like production data, including a deliberately messy version you'll clean in Phase 2. You always know what the "right" answer should look like, which is how you learn to spot when your own query is wrong.

    Git & GitHub

    Git is your project's time machine. GitHub is where that history becomes a public portfolio.

    What it is

    Git is a program installed on your computer that tracks every change you make to a project folder, in checkpoints called commits. GitHub is a website that stores a copy of that history online, so employers, teammates, and future-you can see it.

    Why data engineers use it

    Every mini-project and portfolio project in this bootcamp gets committed to Git and pushed to GitHub. Your GitHub profile is your resume as a career shifter — it's proof you can actually build things, not just say you can.

    How to get it running

      Download Git from git-scm.com/downloads and install with default options.
    2. 2

    3. 3

    4. 4

    How Git Actually Works

    Git moves your work through three places. Understanding this diagram now will save you real confusion later — almost every Git error a beginner hits comes from not knowing which of these three states their file is in.

    A file moves left to right: you edit it, you `add` it to staging, you `commit` it to local history, you `push` it to GitHub.

    TermMeaning
    Repository (repo)A project folder that Git is tracking.
    CommitA saved checkpoint, with a short message describing what changed.
    Stage / git addMarking which changed files should go into the next commit.
    PushUploading your local commits to GitHub.
    CloneDownloading a copy of a GitHub repo onto your computer.
    the five commands you'll type more than any others in this bootcamp
    git init                        # start tracking this folder
git status                      # what changed since the last commit?
git add .                       # stage everything that changed
git commit -m "first commit"    # save a checkpoint
git push                        # upload to GitHub

    A daily habit, not a one-time event

    Run git add . && git commit -m "..." every time you finish a small, working piece of code — not just at the end of the day. Small commits with clear messages are what a real engineering team (and a hiring manager skimming your GitHub) expects to see.

    Variables, Types & Operators

    The building blocks every Python script is made of. We'll represent one BrightCart order in code and never let go of that example.

    What Is a Variable?

    A variable is a labeled box in your computer's memory. You put a value inside it, and you use the label to find that value again later. In Python you create one with a single equals sign — there's no need to declare a type up front, Python figures that out for you (this is called dynamic typing).

    representing one row from customers.csv as variables
    customer_id = "C001"
customer_name = "Ana Dela Cruz"
order_total = 792.34
is_paid = True

print(customer_name)   # Output: Ana Dela Cruz

    Read `=` as "gets set to", not "equals"

    In math, x = 5 is a statement of fact. In Python, customer_id = "C001" is an instruction: take the value on the right, and store it in the box named on the left. That's why count = count + 1 makes perfect sense in code but none in algebra.

    Variable Naming Rules

    Python is strict about what a variable name can look like, and the community is strict about what it *should* look like. Both matter — one crashes your program, the other makes your code readable to the next engineer (often future-you).

    RuleExample
    ✓ snake_case (recommended)customer_id, total_sales
    ✗ No spacescustomer id — this crashes
    ✗ No leading numbers1st_order — this crashes
    ⚠ Case sensitiveTotal and total are different variables

    Core Data Types

    Every value in Python has a type, and the type decides what you're allowed to do with it — you can add two numbers, but adding a number to text will raise an error. These four types cover the vast majority of what you'll touch in this bootcamp.

    TypeDescriptionBrightCart example
    str (string)Text, always in quotes"Manila"
    int (integer)Whole numbers1001  (an order_id)
    floatDecimal numbers24.99  (a unit_price)
    bool (boolean)True or FalseTrue  (is_paid)
    use type() any time you're unsure what you're working with
    order_id = 1001            # int

unit_price = 24.99         # float
is_paid = True              # bool

print(type(unit_price))    # <class 'float'>

    Type Casting: Input Is Always Text

    This trips up nearly every beginner exactly once: Python's input() function always returns a string, even if the person types a number. If you try to do math on it directly, Python either crashes or does something you didn't expect.

    the beginner trap
    qty = input("Quantity: ")   # user types: 3
total = qty * 10
# qty is the STRING "3", not the number 3
# Python repeats the text instead of doing math:
print(total)   # "333333333333333333333333333333"
    the fix — wrap input() in int() or float()
    qty = int(input("Quantity: "))   # convert to int immediately
total = qty * 10
print(total)   # 30
    FunctionConverts to
    int(x)whole number
    float(x)decimal number
    str(x)text

    Operators: Doing Things With Values

    Operators are the symbols that combine values — arithmetic for math, comparisons for true/false questions, and logical operators for combining multiple conditions.

    CategoryOperatorsExample (BrightCart order_items)
    Arithmetic+ - * / // % **quantity * unit_price
    Comparison== != > < >= <=status == "paid"
    Logicaland, or, notstatus == "paid" and amount > 100
    computing one order_items line total
    quantity = 2

print(line_total)          # 49.98

print(is_big_order)        # True

    `=` vs `==`

    = assigns a value. == asks "are these equal?" and returns True/False. Mixing them up (if status = "paid":) is a syntax error in Python — which is actually a mercy; some languages let this typo through silently and cause much worse bugs.

    Working With Strings

    Text data from the real world is almost never clean — extra spaces, inconsistent capitalization, stray characters. String methods are the tools you'll reach for constantly, both here and later when cleaning BrightCart's messier exports in Phase 2.

    string methods you'll use constantly

print(city.upper())        # "  MANILA  "
print(city.lower())        # "  manila  "

email = "ana.delacruz@brightmail.com"

# f-strings: the modern way to build text with variables inside

    Control Flow & Data Structures

    How to make decisions, repeat work, and hold more than one value at a time — the tools that turn single-line scripts into real programs.

    Conditionals: if / elif / else

    Conditionals let your code make decisions. Python checks each condition top to bottom and runs the first block that evaluates to True — everything else is skipped.

    classifying one BrightCart order
    status = "paid"
amount = 792.34

if status == "cancelled":
    print("No action needed")
elif status == "paid" and amount >= 500:
    print("VIP order — flag for priority shipping")
elif status == "paid":
    print("Standard paid order")
else:
    print("Needs follow-up: " + status)

    Indentation is not optional

    Python uses indentation (4 spaces, consistently) to know what's inside an if block and what isn't. Mixing tabs and spaces is one of the most common beginner errors — configure VS Code to insert spaces when you press Tab (it does this by default for Python files).

    Loops: for and while

    A for loop repeats code once per item in a collection — the workhorse of data engineering, since almost everything you process is a list of records. A while loop repeats until a condition becomes False, useful when you don't know in advance how many times you'll need to run.

    for loop — summing a list of order amounts
    order_amounts = [792.34, 59.99, 218.00, 38.97]

total = 0
for amount in order_amounts:
    total = total + amount

print(f"Total revenue: {total}")   # Total revenue: 1109.3
    while loop — a pattern you'll reuse for API pagination in Week 2
    page = 1
has_more_pages = True

while has_more_pages:
    print(f"Fetching page {page}...")
    if page == 3:              # pretend the API told us this was the last page
        has_more_pages = False
    page += 1                  # same as: page = page + 1

    The infinite loop

    A while loop with a condition that never becomes False will run forever and freeze your program. Always make sure something inside the loop moves you toward the exit condition — in the example above, that's page += 1.

    Lists: An Ordered Collection

    A list holds multiple values in one variable, in order, accessed by position (starting at 0, not 1 — this catches everyone once). Lists are the closest thing Python has to a spreadsheet column, and you'll use them constantly before you meet pandas in Phase 2.

    lists — the last line is a list comprehension, a compact filter (optional, come back to this later if it's confusing)
    cities = ["Manila", "Cebu City", "Davao City", "Singapore"]

print(cities[0])          # "Manila"    <- index 0 is the FIRST item
print(cities[-1])         # "Singapore" <- -1 is the LAST item
print(len(cities))        # 4

cities.append("Tokyo")    # add to the end
print(cities)             # ['Manila', 'Cebu City', 'Davao City', 'Singapore', 'Tokyo']

philippine_cities = [c for c in cities if c != "Singapore" and c != "Tokyo"]
print(philippine_cities)  # ['Manila', 'Cebu City', 'Davao City']

    Dictionaries: Labeled Data

    A dictionary stores key–value pairs instead of positions — this is how you'll represent one row of a table before pandas does it for you automatically. If a list is a column, a dictionary is closer to a single record.

    dictionaries — one BrightCart order as a record
    order = {
    "order_id": 1001,
    "customer": "Ana Dela Cruz",
    "amount": 792.34,
    "status": "paid"
}

print(order["customer"])       # "Ana Dela Cruz"
print(order.get("status"))     # "paid"
print(order.get("discount", 0))  # 0  <- .get() with a default avoids a crash if the key is missing

order["shipped"] = True        # add a new key
print(order.keys())            # dict_keys(['order_id', 'customer', 'amount', 'status', 'shipped'])

    A list of dictionaries is exactly how you'll represent a whole table — and it's exactly the shape a JSON API response usually arrives in, which is why this pattern matters so much.

    a list of dictionaries = a small table
    orders = [
    {"order_id": 1001, "customer": "Ana Dela Cruz", "amount": 792.34, "status": "paid"},
    {"order_id": 1002, "customer": "Ben Santos",    "amount": 59.99,  "status": "paid"},
    {"order_id": 1004, "customer": "Carlo Reyes",   "amount": 38.97,  "status": "pending"},
]

paid_total = 0
for o in orders:
    if o["status"] == "paid":
        paid_total += o["amount"]

print(f"Paid revenue: {paid_total}")   # Paid revenue: 852.33

    Tuples & Sets (Brief)

    Two more collection types worth recognizing, even if you'll reach for them less often than lists and dictionaries.

    TypeOrdered?Can change after creation?Duplicates allowed?Written as
    listYesYesYes[1, 2, 3]
    tupleYesNoYes(1, 2, 3)
    setNoYesNo{1, 2, 3}
    a classic use of set(): finding distinct values, before you learn SQL's DISTINCT

unique_methods = set(payment_methods)
print(unique_methods)     # {'gcash', 'credit_card', 'paypal'}  -- duplicates gone

    Functions, Files & Your First Data Extraction

    Functions turn repeated code into reusable tools. Files and APIs are how real data gets into your programs in the first place.

    Functions: Reusable Blocks of Logic

    A function is a named, reusable block of code. Instead of retyping the same logic for every order, you write it once, give it a name, and call it as many times as you need with different inputs (called parameters or arguments).

    anatomy of a function: def, parameters, a default value, and return
    def calculate_line_total(quantity, unit_price):
    return quantity * unit_price

# call it as many times as you need:
print(calculate_line_total(2, 24.99))   # 49.98
print(calculate_line_total(1, 129.00))  # 129.0

def classify_order(amount, threshold=500):
    """threshold has a DEFAULT value -- callers can override it or skip it"""
    if amount >= threshold:
        return "VIP"
    return "standard"

print(classify_order(792.34))         # "VIP"       (uses default threshold=500)
print(classify_order(300, 250))       # "VIP"       (override: threshold=250)
    PartWhat it means
    defkeyword that starts a function definition
    calculate_line_totalthe function's name — use a verb, describe what it does
    (quantity, unit_price)parameters — the inputs the function expects
    returnsends a value back to whoever called the function

    A good function does one thing

    If you find yourself describing a function with "and" ("it calculates the total and prints a receipt and saves to a file"), split it into three functions. Small, single-purpose functions are dramatically easier to test and reuse — this habit pays off enormously once you're writing ETL pipelines in Phase 2.

    Handling Errors: try / except

    Real data is unpredictable — a field might be blank, a file might not exist, an API might time out. try / except lets your program catch an error and respond sensibly instead of crashing.

    skip bad values instead of letting one bad row kill the whole script
    raw_quantities = ["2", "3", "N/A", "1"]

total_units = 0
for q in raw_quantities:
    try:
        total_units += int(q)
    except ValueError:
        print(f"Skipping bad value: {q!r}")

print(total_units)   # 6  (the 'N/A' was skipped, not crashed on)

    Don't catch every error blindly

    A bare except: (with no error type) silently swallows everything, including bugs in your own code — making them nearly impossible to find. Always name the error you expect, like except ValueError:.

    Reading & Writing CSV Files

    Before pandas (Phase 2) makes this effortless, it's worth understanding what's actually happening: a CSV file is plain text with commas separating values, and Python's built-in csv module turns each line into a list — or, with DictReader, into a dictionary using the header row as keys.

    reading customers.csv with csv.DictReader — each row becomes a dictionary
    import csv

with open("data/customers.csv", "r") as f:
    reader = csv.DictReader(f)
    for row in reader:
        print(row["first_name"], row["city"])

# Ana Manila
# Ben Cebu City
# Carlo Davao City
# ...
    writing a new CSV file — the pattern you'll reuse for every pipeline's output
    import csv

vip_customers = [
    {"customer_id": 1, "customer_name": "Ana Dela Cruz", "total_spent": 792.34},
    {"customer_id": 12, "customer_name": "Liam Brooks", "total_spent": 476.00},
]

with open("data/vip_customers.csv", "w", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=["customer_id", "customer_name", "total_spent"])
    writer.writeheader()
    writer.writerows(vip_customers)

    with open(...) as f:

    The with keyword automatically closes the file when you're done with it, even if an error happens inside the block. Always use with open(...) instead of a bare open(...) — it's the difference between a script that occasionally corrupts files and one that never does.

    Working With JSON & APIs

    JSON (JavaScript Object Notation) is the format almost every API speaks — and it maps directly onto Python dictionaries and lists, which is exactly why you learned those first. An API is just a website's URL that returns data instead of a webpage.

    a JSON order record — notice it's basically a Python dict with a list inside it
    {
  "order_id": 1001,
  "customer": "Ana Dela Cruz",
  "items": [
    {"product": "Wireless Mouse", "quantity": 2},
    {"product": "Water Bottle", "quantity": 1}
  ],
  "status": "paid"
}
    json.load() turns JSON text into Python dictionaries/lists automatically
    import json

with open("data/order_1001.json") as f:
    order = json.load(f)     # JSON text -> Python dict

print(order["customer"])            # "Ana Dela Cruz"
for item in order["items"]:
    print(item["product"], item["quantity"])
    requests — the standard library for calling real APIs (install with: pip install requests)
    import requests

response = requests.get("https://api.example.com/orders", timeout=30)
response.raise_for_status()   # crash loudly if the request failed, instead of silently continuing

data = response.json()        # parses JSON straight into a Python dict/list
print(data[0]["customer"])

    Always set a timeout

    Without timeout=30, a stalled server can freeze your script forever with no error at all. This one keyword argument will save you a genuinely confusing debugging session down the road.

    WEEK 3 · SQL FUNDAMENTALS

    Talking to a Database

    SQL is how you ask a database questions. We'll load BrightCart into a real database and start asking it things.

    What Is a Relational Database?

    A relational database stores data in tables — grids of rows and columns, like a spreadsheet, except tables can be linked together by shared ID columns (that's the "relational" part). PostgreSQL, MySQL, and SQLite are all RDBMS (Relational Database Management Systems) — programs that store and let you query this kind of data.

    Python variables live only while your script runs. A database persists — BrightCart's orders stay there whether your laptop is on or off, and multiple programs (or people) can read and write to it at the same time. That durability and shareability is exactly why production systems use databases instead of just CSV files.

    Tool Spotlight: PostgreSQL

    20 min

    Tool Spotlight

    PostgreSQL ("Postgres")

    A free, open-source relational database — the one this entire bootcamp is built around.

    What it is

    PostgreSQL is a server program: it runs quietly in the background on your computer (or in the cloud, later in Phase 2) and listens for SQL commands from clients like the terminal, VS Code, or a Python script.

    Why data engineers use it

    It's free, it's what most real companies actually use for OLTP workloads, and everything you learn here — joins, window functions, indexes — transfers directly to Snowflake, BigQuery, and Redshift in Phase 2.

    3. 3

    4. 4

    SELECT, WHERE, ORDER BY, LIMIT

    Every SQL query starts the same way: tell it what columns you want, from which table, which rows qualify, and how to sort the result. This one pattern answers most of the questions a business ever asks.

    the 5 most fundamental keywords in SQL, in the order you'll type them
    SELECT first_name, last_name, city
FROM customers
WHERE country = 'Philippines'
ORDER BY city ASC
LIMIT 5;
    ClauseWhat it does
    SELECTwhich columns to return (or * for all of them)
    FROMwhich table to read
    WHEREfilters rows before they're returned
    ORDER BYsorts the result — add DESC for descending
    LIMITcaps how many rows come back
    a realistic BrightCart question: "what's still waiting on us?"
    -- Every order that is still pending, most recent first
SELECT order_id, order_date, payment_method
FROM orders
WHERE status = 'pending'
ORDER BY order_date DESC;

    SQL strings use single quotes

    WHERE status = "paid" will error in Postgres — use single quotes for text: WHERE status = 'paid'. Double quotes in SQL mean something entirely different (they quote column/table names, not values).

    Aggregate Functions & GROUP BY

    Aggregate functions collapse many rows into one summary number — count, sum, average, min, max. GROUP BY is what lets you get one summary per category instead of one summary for the whole table.

    FunctionReturns
    COUNT(*)number of rows
    SUM(col)total
    AVG(col)average
    MIN(col) / MAX(col)smallest / largest value
    how many orders are in each status?
    SELECT status, COUNT(*) AS order_count
FROM orders
GROUP BY status
ORDER BY order_count DESC;
    statusorder_count
    paid39
    pending3
    cancelled2
    refunded1
    HAVING filters groups AFTER aggregation — WHERE can't do this, it runs before grouping
    -- Total revenue per payment method, but only for orders worth summarizing
SELECT payment_method,
       SUM(quantity * unit_price) AS revenue,
       COUNT(*) AS line_items
FROM order_items oi
JOIN orders o ON o.order_id = oi.order_id
WHERE o.status = 'paid'
GROUP BY payment_method
HAVING SUM(quantity * unit_price) > 200
ORDER BY revenue DESC;

    WHERE vs HAVING

    WHERE filters individual rows before grouping happens. HAVING filters the groups after SUM/COUNT/etc. have already been calculated. If your condition mentions an aggregate function, it has to go in HAVING.

    WEEK 3–4 · SQL DEEP DIVE

    Joins, Subqueries & Window Functions

    Real BrightCart questions almost always need more than one table. This is how you combine them.

    Primary Keys, Foreign Keys & the ERD

    A primary key uniquely identifies each row in a table (customer_id in customers). A foreign key is a column in one table that points at a primary key in another (orders.customer_id points at customers.customer_id). This is the entire mechanism that lets SQL connect tables together.

    JOIN Types

    A JOIN combines rows from two tables based on a matching column. Which rows survive when there isn't a match depends entirely on which join type you pick — this is the single most important SQL concept to get comfortable with.

    Join typeKeeps...
    INNER JOINonly rows that match in both tables
    LEFT JOINall rows from the left table, matched data if it exists, else NULL
    RIGHT JOINall rows from the right table (rarely needed — just swap table order and use LEFT)
    FULL JOINeverything from both sides, matched where possible

    The "find what's missing" pattern

    LEFT JOIN ... WHERE right_table.id IS NULL is how you find customers with no orders, products that never sold, or — later in Phase 2 — records that failed to load. Memorize this shape.

    Window Functions

    A window function calculates something across a set of related rows without collapsing them into one row the way GROUP BY does — you keep every row, and get a ranking, running total, or comparison alongside it. This is the tool that makes "top N per group" and "running total" questions easy.

    FunctionReturns
    ROW_NUMBER()1, 2, 3... with no ties
    RANK()ties share a rank, next rank skips (1, 1, 3)
    SUM() / AVG() OVER (...)running total / running average
    LAG() / LEAD()the previous / next row's value

    Chapter 6 Checklist — before moving on, you should be able to:

    • Explain the difference between INNER JOIN and LEFT JOIN in one sentence
    • Use LEFT JOIN ... WHERE x IS NULL to find "missing" records
    • Rewrite a nested subquery as a WITH CTE
    • Use ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) to rank rows within a group

    WEEK 4 · DIMENSIONAL MODELING

    Building a Reporting Layer

    The tables you query for daily operations aren't the tables you want to build dashboards on. Here's the design pattern that fixes that.

    OLTP vs OLAP

    customers, orders, and order_items are OLTP tables (Online Transaction Processing) — designed so BrightCart's checkout page can insert one order quickly and safely. A dashboard asking "what were our total sales by category, by month?" has completely different needs — that's OLAP (Online Analytical Processing), and the design pattern for it is called a star schema.

    The Star Schema: Facts & Dimensions

    A fact table holds the numbers you want to measure (sales_amount, quantity) plus foreign keys pointing out to dimension tables, which hold the descriptive context (who, what, when).
